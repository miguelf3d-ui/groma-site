Button

Stable
Updated 14 July 2026 v3.2.0 Owned by Payments Platform

Buttons commit a person to an action — sending a payment, approving a limit change, closing an account. In Cadence they are deliberately scarce: one primary action per view, and never more than one action that moves money.

Overview

A button is the only control in Cadence that performs an action immediately on activation. If the control navigates somewhere instead — a statement, a counterparty record, an external help article — use Link, which renders an anchor and inherits browser behaviours people expect, like open-in-new-tab.

Every screen should have a clear answer to “what is the one thing I am meant to do here?”. Cadence enforces this with a single primary button per view. Secondary and ghost variants carry everything else, and the destructive variant is reserved for irreversible operations that a support agent cannot undo on the customer’s behalf.

Money-moving actions must pass a confirmation step. Pair the button with ConfirmDialog and set requiresStepUp when the amount exceeds the customer’s per-transaction threshold — the button itself never initiates a transfer directly.

Props

All unlisted props are forwarded to the underlying <button> element. Required props are marked with an asterisk.

PropTypeDefaultDescription
children* ReactNode — The label. Use a verb phrase describing the outcome (“Approve transfer”), not a generic confirmation (“OK”).
variant "primary" | "secondary" | "ghost" | "destructive" "secondary" Visual weight and intent. Only one primary may be mounted per view; the dev-mode runtime warns on the second.
size "sm" | "md" | "lg" "md" Control height: 28 / 34 / 42px. Use sm inside dense tables, lg only for a single focal action on marketing or onboarding surfaces.
iconStart IconComponent undefined 16px icon rendered before the label. Icons are decorative and receive aria-hidden automatically.
iconEnd IconComponent undefined Trailing icon. Reserve for forward motion in a flow (“Continue →”) or for a disclosure affordance.
loading boolean false Swaps the leading icon for a spinner, sets aria-busy, and blocks repeat submits. The label stays visible so the button does not change width.
loadingLabel string "Working…" Announced to screen readers via a polite live region while loading is true.
disabled boolean false Prefer leaving the button enabled and explaining the failure on submit. Disable only when the reason is visible on screen.
fullWidth boolean false Stretches to the container width. Standard on viewports under 480px and inside Drawer footers.
onPress (event: PressEvent) => void — Fires on click, Space and Enter. Normalises pointer and keyboard activation; use instead of onClick.

Usage guidance

Button hierarchy is the fastest signal of whether a screen was designed or assembled. These rules come out of the 2026 payments audit, where 40% of mis-clicks in the transfer flow traced back to two competing primary actions.

Do
  • ●Name the outcome and, where the amount is known, put it in the label. “Send £2,400” reads as a receipt before it is one.
  • ●Keep one primary per view and give the escape route the lowest weight available.
  • ●Hold the button in loading until the server confirms — optimistic success states are not acceptable for money movement.
Don’t
  • ●Don’t stack competing primaries. Two heavy buttons force people to read both before acting, which is where the mis-clicks come from.
  • ●Don’t use vague labels like “OK” or “Submit”. They fail on a screen reader stripped of surrounding context.
  • ●Don’t use the destructive variant for merely inconvenient actions — reserve red for what cannot be reversed.

Typography scale

Accessibility

Every variant is tested against WCAG 2.2 AA in both themes. Contrast is measured on the button’s own resting background, and focus indicators are measured against the surface behind them.

Keyboard interaction

KeyBehaviour
TabMoves focus to the button in DOM order and paints a 2px :focus-visible ring with a 2px offset. Disabled buttons stay in the tab order so their tooltip can explain why they are inactive.
SpaceActivates on key-up. Holding the key does not repeat-fire, which prevents duplicate payment submissions on slow connections.
EnterActivates on key-down. Inside a form, a button of type="submit" also responds to Enter pressed in any text field.
EscNot handled by the button. When it sits in a dialog footer, Esc dismisses the dialog and returns focus to the element that opened it.

ARIA notes

  • Renders a native <button>. Never apply role="button" to a div — you inherit nothing and reimplement everything.
  • Icon-only buttons require aria-label. The build fails on any icon-only button without an accessible name.
  • While loading, the component sets aria-busy="true" and announces loadingLabel through a polite live region. It stays focusable so focus is not lost mid-request.
  • Buttons that open an overlay expose aria-expanded and aria-controls; the overlay traps focus and restores it on close.
  • Target size is at least 24×24px per WCAG 2.2 (2.5.8). The sm size meets this through spacing, not padding — keep 8px between adjacent small buttons.
